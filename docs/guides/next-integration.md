# Next.js integration path

HackKit Web Apps integrate with Core and HackKit UI through **`@hackkit/next`**. After runtime-owned page guards and the collapsed Core action bridge, there is one coherent path for:

1. Runtime setup
2. Page guards
3. Core mutations / server actions
4. HackKit UI provider wiring

Package README: [`packages/next/README.md`](../../packages/next/README.md). Reference implementation: [`apps/test-web`](../../apps/test-web).

## Why one path

Earlier apps could rebuild page guards locally and duplicate the full Core action surface in both server actions and UI provider maps. That made every new mutation a multi-file app change and let Core, Next, and UI drift apart.

The simplified path keeps construction inside `@hackkit/next`:

| Concern        | Own it in               | App does                       |
| -------------- | ----------------------- | ------------------------------ |
| Runtime        | `createHackkitRuntime*` | Call once, `setHackkitRuntime` |
| Page guards    | `runtime.pageGuards`    | `getPageGuards()` in layouts   |
| Mutations      | `runtime.mutations`     | Nothing for Core actions       |
| UI actions     | `hackKitUIActions`      | Pass into `HackKitUIProvider`  |
| Plugin actions | Generated by CLI sync   | Import generated module        |

## Wiring checklist

### Runtime

`apps/test-web/lib/runtime.ts` is the composition root:

-   `createHackkitRuntimeFromConfig({ config, database, auth, afterCurrentUser? })`
-   `setHackkitRuntime(runtimePromise)` so `"use server"` actions can resolve mutations
-   Thin accessors: `getRuntime`, `getCurrentUser`, `getHackkit`, `getPageGuards`

Use `afterCurrentUser` for app-specific work that must run for both `getCurrentUser` and guards (for example owner allowlist provisioning).

### Provider

`apps/test-web/app/providers.tsx`:

```tsx
<HackKitUIProvider actions={hackKitUIActions} />
```

Import `hackKitUIActions` from `@hackkit/next`. Do not rebuild the map in the app.

Omit `routes` (or pass only serializable string overrides) from the Server Component provider. Admin route builders are created inside the client provider defaults. Custom builders belong on a client `navigation` adapter. Server helpers such as onboarding step construction may still use `hackKitUIRoutes` / `DEFAULT_HACKKIT_UI_ROUTES` outside the provider.

### Layouts and pages

| Area                                                 | Guard / data                                                          | UI actions                                           |
| ---------------------------------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------- |
| Onboarding                                           | `requireOnboardingAccess` (+ registration-open where needed)          | `claimHackTag`, `completeUserData`, `registerHacker` |
| Participant (dashboard, pass, settings, RSVP, teams) | `requireParticipantAccess`                                            | profile, RSVP, Event Pass consumers                  |
| Approval pending                                     | `requireApprovalPendingAccess`                                        | —                                                    |
| Admin                                                | `requireNotBanned` + `requirePermission(Admin)` (+ finer permissions) | admin console, scanners, settings                    |

Plugin pages (Teams, Discord, invites) use the registered runtime and generated plugin actions; they are not part of `hackKitUIActions`.

### Do not

-   Call `createPageGuards` in the app
-   Call `createHackKitMutations` in the app
-   Hand-maintain a local Core action export list for the provider
-   Duplicate mutation wiring when adding a Core UI action — extend `@hackkit/next` instead

## Drift protection

`@hackkit/next` tests assert that:

-   `hackKitUIActions` keys match `HackKitUIActions`
-   `createHackKitMutations` returns the same key set
-   Named exports in `actions.ts` match that key set
-   Page guards redirect / not-found for incomplete onboarding, unapproved users, bans, and closed registration

Compile-time: `hackKitUIActions satisfies HackKitUIActions`.

```bash
pnpm --filter @hackkit/next test
pnpm --filter @hackkit/next typecheck
pnpm --filter test-web typecheck
pnpm --filter test-web build
```
